# Data Augmentation in Deep Learning

Data augmentation manufactures extra training examples by applying small, label-preserving
changes to the images you already have: rotate a cat photo a few degrees, zoom in, flip it,
darken it. The model then sees a slightly different version of every image each epoch, so it
can't succeed by memorizing exact pixels and has to learn what stays the same across the
changes. That is the whole idea, and it is cheap, which is why it is one of the first things
to try when a model overfits a small dataset. This document builds the standard transforms from
scratch, then tests the video's claims directly: a tiny training set trained with and without
augmentation, how the gain depends on dataset size, what actually goes wrong if you augment
the test data, and how much augmentation is enough. Everything here was run; one hypothesis I
expected to confirm (that too much augmentation hurts) was **not** observed, and that is
reported as measured. All images are synthetic and generated by code, since this environment
has no internet access or real photo datasets.

This builds on [convolution-operation.md](convolution-operation.md) and
[pooling-layer.md](pooling-layer.md) (the model used in the experiments is a small CNN made of
those pieces), and it is the standard remedy for the overfitting discussed in
[pretrained-models.md](pretrained-models.md), where limited labeled data is the core problem.
Optimizers are covered in [adam.md](adam.md).

## 1. Why augment: overfitting and invariance

A network with far more capacity than data can drive its training error to zero by memorizing
the training set, and then fail on new images. Two things make augmentation effective against
this:

- **More variety from the same data.** Each epoch the model sees a different random variant of
  each image, so the effective training set is much larger than the stored one, though the
  variants are correlated with their source and are not as good as genuinely new photos.
- **Built-in invariance.** If a dog stays a dog when shifted, rotated by 15°, or mirrored, then
  training on those variants pushes the network to give the same answer for them. This is the
  "learn features that don't depend on orientation" point from the video, and it is a way of
  telling the model about symmetries you know hold but that your small dataset doesn't
  demonstrate.

The second point also says when augmentation works and when it doesn't: it helps when the
training set **under-represents the variation the model will face**. If your handful of
training images already cover the poses, distances, and lighting you will see later, there is
nothing for augmentation to add. Section 4 shows this directly, because my first version of the
experiment made exactly that mistake.

## 2. The transforms, built from scratch

The geometric transforms in `ImageDataGenerator` are all 2D **affine warps**: for every output
pixel $(x, y)$ compute where it came from in the input, $(x', y')$, by a linear map, and copy
that pixel:

$$\begin{bmatrix} x' \\ y' \end{bmatrix} = \begin{bmatrix} a & b \\ c & d \end{bmatrix}\begin{bmatrix} x \\ y \end{bmatrix} + \begin{bmatrix} t_x \\ t_y \end{bmatrix}$$

Rotation by angle $\theta$ about the image center, zoom by factor $z$, translation, and shear
are just different choices of the matrix and offset (rotation uses $a=d=\cos\theta$,
$b=-c=\sin\theta$; zoom uses $a=d=1/z$; a horizontal flip just reverses the column order).
Brightness is not geometric: it multiplies pixel values by a factor and clips to $[0,1]$.

![Transform gallery](https://raw.githubusercontent.com/versatilerajan/deepcontent/main/images/01_transform_gallery.png)

*Each transform applied to the same synthetic "dog-like" image (a body, a head, and an ear,
asymmetric on purpose so flips and rotations are visible). All of these were computed by the
from-scratch code in [section 10](#10-from-scratch-numpy-implementation), using nearest-neighbor
resampling. Exposed borders are filled with black here, whereas Keras' default fills them by
repeating the nearest edge pixel (`fill_mode='nearest'`), so Keras output looks slightly
different at the edges. The rotation sign convention is arbitrary, and it doesn't matter in
practice because augmentation samples the angle symmetrically around zero.*

## 3. One image, many versions

Real augmentation draws a fresh random combination of these transforms every time an image is
loaded. Drawing 12 random versions of the single source image above:

![One image, many versions](https://raw.githubusercontent.com/versatilerajan/deepcontent/main/images/02_one_image_many_versions.png)

*Twelve augmented versions of one image, each a random mix of rotation, zoom, shift, shear,
flip, and brightness. They are all clearly the same animal but no two are alike: measured over
all 66 pairs of versions there were **0** identical pairs, with a mean pixel-space L2 distance
of **26.8** between pairs (26.8 is not meaningful on its own, only in comparison with 0 for
identical images). This is what the video means by generating "multiple augmented versions" of
a single image.*

## 4. The experiment: a tiny training set

To test the central claim, a small CNN (two conv+pool blocks and two dense layers, built from
the same from-scratch layers as earlier notes) was trained to tell two synthetic classes apart,
"cat-like" (narrow body, pointed ears) and "dog-like" (wide body, round ears), on **only 12
training images per class** (24 total), with validation and test sets of 80 and 120 images.

![The small training set](https://raw.githubusercontent.com/versatilerajan/deepcontent/main/images/03_small_training_set.png)

*The training images: within each class they differ only by a couple of pixels of position
jitter, like a set of very similar photos taken under the same conditions.*

The validation and test images are deliberately more varied than this: larger position jitter
plus a random rotation of up to ±25° and a random zoom of up to ±15%, modeling the range of
poses and distances real photos have. The training set never shows the network any rotation
or zoom.

**A negative result first.** My initial version of this experiment generated train, validation,
and test images all with the same modest jitter. Every configuration, augmented or not, reached
**100%** on all three sets with zero overfitting gap. The task simply didn't need augmentation,
because the tiny training set already covered the variation in the test set. Only after
making the training set narrower than the test distribution did augmentation have anything to
fix, which is the condition described in [section 1](#1-why-augment-overfitting-and-invariance).
So the result below shows augmentation helping *when there is a train/test variation gap*, not
that it helps unconditionally.

---

## 5. Result: the overfitting gap closes

Both models train for 35 epochs on the same 24 images with identical settings; the augmented
one draws a fresh random rotation (±15°), zoom (±15%), shift (±10%), shear (±8°), flip, and
brightness change (±15%) for every image every epoch. Averages over 3 random seeds:

| | train accuracy | validation accuracy | train − val gap | test accuracy |
|---|---|---|---|---|
| no augmentation | 100% | 83.3% | **16.7 pp** | 84.4% (sd 12.0) |
| with augmentation | 100% | 99.2% | **0.8 pp** | 99.7% (sd 0.4) |

(Training accuracy is measured on the original, unaugmented 24 images in both cases.)

![Overfitting comparison](https://raw.githubusercontent.com/versatilerajan/deepcontent/main/images/04_augmentation_overfitting.png)

*(a) Training accuracy (dashed) reaches 100% for both models, but validation accuracy (solid)
for the unaugmented model levels off around 83% while the augmented model's climbs to about
99%. The augmented curves are noisier during training, which is expected since every epoch
presents different images. (b) The train − validation gap, the standard symptom of overfitting,
is 16.7 percentage points without augmentation and 0.8 with it. Final test accuracy goes from
84.4% to 99.7%, and the seed-to-seed standard deviation drops from 12.0 to 0.4 points, so the
augmented model is also far more reliable from run to run.*

This is the claim from the video, reproduced: with very little data, augmentation turned a
model that memorized its training set into one that generalizes. The caveat from section 4
applies, since the size of the gain depends on how much variation the test data has that the
training data lacks.

## 6. Does dataset size matter?

Repeating the comparison with 6, 25, and 50 training images per class (2 seeds per point, 25
epochs, so this is noisier than the main experiment):

| images per class | no augmentation | with augmentation | gain |
|---|---|---|---|
| 6 | 77.5% | 90.4% | +12.9 pp |
| 25 | 89.2% | 100.0% | +10.8 pp |
| 50 | 96.2% | 100.0% | +3.8 pp |

![Benefit versus dataset size](https://raw.githubusercontent.com/versatilerajan/deepcontent/main/images/05_benefit_vs_dataset_size.png)

*Accuracy against training-set size. The unaugmented model improves steadily as it sees more
images, while the augmented one is near its ceiling from 25 images per class on, so the gap
narrows from about 13 points at 6 images per class to under 4 at 50. This matches the general
expectation that augmentation matters most when data is scarce. With only 2 seeds per point
and a single dataset, the middle and last gains (10.8 and 3.8 points) should be read as
"shrinking", not as a precise curve.*

## 7. Why augment only the training data

The video's key caveat is that augmentation should be applied to training data only, so that
evaluation stays objective. Two things go wrong if you augment the evaluation data too, and both
were measured by evaluating one **frozen** trained model (the augmented-training model from
seed 0) 40 times, once on the plain test set and once on a freshly re-augmented copy of it each
time:

| | reported test accuracy |
|---|---|
| plain test set | **99.17%** every time (sd 0.00 pp) |
| freshly augmented test set | mean **95.2%**, sd **1.7 pp**, range 91.7% – 99.2% |

![Why not augment test data](https://raw.githubusercontent.com/versatilerajan/deepcontent/main/images/06_why_not_augment_test_data.png)

*The model never changes between evaluations, yet the augmented-test-set metric wanders across
a 7.5-point range purely because of which random rotations and shifts each image happened to
get. (1) It is **noisy**: two evaluations of the same model disagree, so you can't tell a real
improvement from luck. (2) It is **biased**: the mean (95.2%) is lower than the true
plain-test-set figure (99.2%), because you are now measuring accuracy on a harder, distorted
distribution rather than on the images you actually care about.*

One legitimate exception: **test-time augmentation** deliberately averages a model's
predictions over several augmented copies of each test image to get a more stable prediction.
That is a prediction technique, done with a fixed procedure, and the reported metric is still
computed against the real labels. It is not the same as evaluating on randomly distorted data
and reporting that accuracy as the model's accuracy. Krizhevsky et al. (2012) used a version of
this (averaging over 10 image patches) for AlexNet's test predictions.

Frameworks make the training-only rule easy to follow: Keras preprocessing layers such as
`RandomRotation` only act during training and pass images through unchanged at evaluation and
prediction time ([section 9](#9-implementation-in-keras)).

## 8. How strong should augmentation be?

The usual advice is that too little augmentation doesn't help and too much distorts the data
until it stops resembling the test distribution. I tested this by scaling all the augmentation
ranges from section 5 by a multiplier (0 = none, 1 = the main experiment's settings), 3 seeds
per point:

| strength | 0 | 0.5 | 1 | 1.5 | 2.5 | 4 |
|---|---|---|---|---|---|---|
| test accuracy | 84.4% | 95.0% | 99.7% | 100% | 100% | 100% |

![Augmentation strength sweep](https://raw.githubusercontent.com/versatilerajan/deepcontent/main/images/07_augmentation_strength_sweep.png)

*Test accuracy climbs from 84.4% with no augmentation to the ceiling by about 1.5× the default
strength, with the spread across seeds shrinking to zero at the same time. Contrary to the
usual warning, **accuracy did not fall even at 4× strength** (rotation up to ±60°, zoom ±60%).
So the "too much hurts" half of the advice was not reproduced here.*

That is a result about this setup, not a general rule. The test images here vary by at most
±25° rotation and ±15% zoom, so stronger augmentation just covered that range more thoroughly
without ever producing images that contradict a label. Real tasks differ: augmentation can
hurt when a transform **changes the correct label**: a 180° rotation turns a "6" into a "9",
and a horizontal flip turns a "b" into a "d", so those transforms would teach the network wrong
answers. It can also hurt when it pushes training images far from the test distribution. I did not
test label-altering transforms here, so treat that warning as standard practice from the
literature (Shorten & Khoshgoftaar, 2019), not something these experiments verified.

## 9. Implementation in Keras

This environment has no TensorFlow or internet access, so the snippets in this section are
checked for valid Python syntax but have not been executed. They follow the documented Keras
APIs.

**`ImageDataGenerator` (the approach in the video).** Note the two separate generators: one
with augmentation for training, one that only rescales for validation, which is the
training-only rule from section 7 in code:

```python
from tensorflow.keras.preprocessing.image import ImageDataGenerator

# Training generator: rescale + random augmentation
train_datagen = ImageDataGenerator(
    rescale=1./255,
    rotation_range=20,        # degrees
    width_shift_range=0.15,   # fraction of width
    height_shift_range=0.15,  # fraction of height
    shear_range=0.1,
    zoom_range=0.15,
    horizontal_flip=True,
    fill_mode='nearest',
)

# Validation generator: rescale ONLY, no augmentation
val_datagen = ImageDataGenerator(rescale=1./255)

train_gen = train_datagen.flow_from_directory(
    'data/train', target_size=(256, 256), batch_size=32, class_mode='binary')
val_gen = val_datagen.flow_from_directory(
    'data/validation', target_size=(256, 256), batch_size=32,
    class_mode='binary', shuffle=False)

history = model.fit(train_gen, epochs=10, validation_data=val_gen)
```

To look at what the generator produces from a single image, as in the video's demonstration:

```python
import numpy as np
import matplotlib.pyplot as plt
from tensorflow.keras.preprocessing.image import ImageDataGenerator, load_img, img_to_array

# No rescale here, so pixel values stay 0-255 and display correctly as uint8
demo_datagen = ImageDataGenerator(rotation_range=20, width_shift_range=0.15,
                                  height_shift_range=0.15, zoom_range=0.15,
                                  horizontal_flip=True, fill_mode='nearest')

img = load_img('cat.jpg', target_size=(256, 256))
x = img_to_array(img)[np.newaxis]          # shape (1, 256, 256, 3): batch of one
aug_iter = demo_datagen.flow(x, batch_size=1)

plt.figure(figsize=(9, 9))
for i in range(9):
    batch = next(aug_iter)                 # a new random variant on every call
    plt.subplot(3, 3, i + 1)
    plt.imshow(batch[0].astype('uint8'))
    plt.axis('off')
plt.show()
```

**Deprecation note.** TensorFlow's API documentation marks
`tf.keras.preprocessing.image.ImageDataGenerator` as **deprecated**, and Keras maintainers point to
`image_dataset_from_directory` for loading plus separate preprocessing layers for augmentation
(a Keras maintainer's answer in the project's issue tracker).
The video's approach still appears in many tutorials and works in current versions, but new
code should use the layer-based version:

```python
import tensorflow as tf
from tensorflow.keras import layers, Sequential

train_ds = tf.keras.utils.image_dataset_from_directory(
    'data/train', image_size=(256, 256), batch_size=32, label_mode='binary')
val_ds = tf.keras.utils.image_dataset_from_directory(
    'data/validation', image_size=(256, 256), batch_size=32, label_mode='binary')

# These layers only augment during training; at evaluate()/predict() time they
# pass the images through unchanged, so validation data stays untouched.
data_augmentation = Sequential([
    layers.RandomFlip('horizontal'),
    layers.RandomRotation(20 / 360),      # factor is a fraction of a full turn
    layers.RandomTranslation(0.15, 0.15),
    layers.RandomZoom(0.15),
])

model = Sequential([
    layers.Input(shape=(256, 256, 3)),
    data_augmentation,
    layers.Rescaling(1. / 255),
    # ... the same Conv2D / MaxPooling2D / Dense stack as before ...
    layers.Flatten(),
    layers.Dense(1, activation='sigmoid'),
])
model.compile(optimizer='adam', loss='binary_crossentropy', metrics=['accuracy'])
history = model.fit(train_ds, epochs=10, validation_data=val_ds)
```

`RandomRotation`'s `factor` is a fraction of a full 360° turn, so `20 / 360` gives about ±20°.
Because the augmentation lives inside the model, it can run on the GPU with the rest of the
network and cannot accidentally be applied to validation data.

## 10. From-scratch NumPy implementation

The core of every geometric transform above, in plain NumPy. This is essentially the code used
to produce the figures and run the experiments; the shear transform and some default parameter
values are simplified or left out for brevity:

```python
import numpy as np

def affine_warp(img, matrix, fill=0.0):
    """matrix (2x3) maps OUTPUT pixel coords (x, y, 1) -> INPUT coords.
       Nearest-neighbor sampling; pixels that map outside the image get `fill`."""
    H, W = img.shape[:2]
    ys, xs = np.meshgrid(np.arange(H), np.arange(W), indexing="ij")
    coords = np.stack([xs.ravel(), ys.ravel(), np.ones(H * W)])   # (3, H*W)
    src = matrix @ coords                                          # (2, H*W)
    sx = np.round(src[0]).astype(int).reshape(H, W)
    sy = np.round(src[1]).astype(int).reshape(H, W)
    valid = (sx >= 0) & (sx < W) & (sy >= 0) & (sy < H)
    out = img[np.clip(sy, 0, H - 1), np.clip(sx, 0, W - 1)]
    mask = valid if out.ndim == 2 else valid[..., None]
    return np.where(mask, out, fill)

def rotate(img, degrees):
    H, W = img.shape[:2]
    cx, cy = (W - 1) / 2, (H - 1) / 2
    th = np.deg2rad(degrees)
    c, s = np.cos(th), np.sin(th)
    M = np.array([[c, s, cx - c * cx - s * cy],
                  [-s, c, cy + s * cx - c * cy]])
    return affine_warp(img, M)

def zoom(img, factor):                        # factor > 1 zooms in
    H, W = img.shape[:2]
    cx, cy = (W - 1) / 2, (H - 1) / 2
    M = np.array([[1 / factor, 0, cx - cx / factor],
                  [0, 1 / factor, cy - cy / factor]])
    return affine_warp(img, M)

def shift(img, dx_frac, dy_frac):
    H, W = img.shape[:2]
    M = np.array([[1, 0, -dx_frac * W], [0, 1, -dy_frac * H]])
    return affine_warp(img, M)

def hflip(img):
    return img[:, ::-1, ...].copy()

def brightness(img, factor):
    return np.clip(img * factor, 0, 1)

def random_augment(img, rng, rotation_range=20, zoom_range=0.15,
                   shift_range=0.1, flip=True, brightness_range=0.15):
    out = rotate(img, rng.uniform(-rotation_range, rotation_range))
    out = zoom(out, 1 + rng.uniform(-zoom_range, zoom_range))
    out = shift(out, rng.uniform(-shift_range, shift_range),
                     rng.uniform(-shift_range, shift_range))
    if flip and rng.random() < 0.5:
        out = hflip(out)
    return brightness(out, 1 + rng.uniform(-brightness_range, brightness_range))
```

Applying the transforms one after another, as `random_augment` does, resamples the image
several times and loses a little sharpness each time; Keras composes them into a single
transform matrix and resamples once.

## 11. Practical guidance

- **Augment only the training data.** Rescale (and nothing else) for validation and test
  ([section 7](#7-why-augment-only-the-training-data)). Preprocessing layers inside the model
  do this automatically.
- **Only use transforms that keep the label true.** Horizontal flips are fine for cats and dogs
  but not for digits or text; large rotations are fine for aerial photos but not for
  upright-object classes where "upside down" is out of distribution. This was not tested here;
  it is standard practice.
- **Match augmentation to the variation you expect at test time.** The measured gain in
  [section 5](#5-result-the-overfitting-gap-closes) came from covering variation (rotation,
  zoom, shift) that the small training set lacked. Augmentation cannot invent a kind of
  variation you have no way to describe, such as a new breed or new camera type.
- **Expect the biggest gains when data is scarce** ([section 6](#6-does-dataset-size-matter)),
  and smaller ones as the dataset grows. It never replaces collecting more real data.
- **Start moderate, then sweep.** [Section 8](#8-how-strong-should-augmentation-be) saw the
  benefit saturate near 1.5× the default here; in a real task, tune strength on the validation
  set, and watch for the point where validation accuracy stops improving.
- **Combine with other regularizers.** Augmentation works alongside dropout and batch
  normalization (as in the cats-vs-dogs model from earlier), and with transfer learning
  ([pretrained-models.md](pretrained-models.md)), where it is applied to your own small target
  dataset.
- **Mind training time.** Augmented training usually needs more epochs to converge, because
  the model never sees the same image twice.

## 12. Key takeaways

1. Data augmentation applies random, label-preserving transforms (rotation, zoom, shift, shear,
   flip, brightness) to training images so the model sees a different variant of each image
   every epoch. A single source image produced 12 versions with no identical pairs.
2. It helps when the training set under-represents the variation the model will face. When the
   train and test distributions were equally easy, augmented and unaugmented models both hit
   100% and augmentation did nothing.
3. With 12 training images per class and a test set containing more pose variety, augmentation
   cut the train − validation gap from **16.7 to 0.8 percentage points** and raised test accuracy
   from **84.4% to 99.7%**, with seed-to-seed standard deviation falling from 12.0 to 0.4.
4. The benefit shrinks as data grows: +12.9 points at 6 images per class, +10.8 at 25, +3.8 at
   50 (2 seeds per point, so approximate).
5. Augmenting evaluation data makes the metric both noisy and biased: evaluating one frozen
   model 40 times gave 99.17% every time on the plain test set, versus a mean of 95.2% with a
   standard deviation of 1.7 points (range 91.7–99.2%) on re-augmented copies.
6. Augmentation strength saturated near 1.5× the default here, and accuracy did **not** fall
   even at 4×. The common warning that too much augmentation hurts was not reproduced in this
   synthetic setup; it remains a real risk for label-altering transforms, which were not tested.
7. In Keras, `ImageDataGenerator` (used in the video) is deprecated in TensorFlow's docs in
   favor of `image_dataset_from_directory` plus preprocessing layers, which only act during
   training and so enforce the training-only rule automatically.
